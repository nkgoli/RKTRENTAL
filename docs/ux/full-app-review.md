# Full app UX review and shared visual baseline

Reviewed 18 October 2026. This is an improvement of the existing application, with the completed five-tab lease workspace as the consistency reference.

## Coverage and evidence basis

The checkout contains **33 page routes**, plus route handlers for downloads, exports, authentication, repairs and provider/notification operations. All **40 screens** in Designs/rocketrental-app revision 283 are mapped below. The foundation update changes the shared stylesheet and the three dashboard screens through revision **288**; it does not replace any other screen.

Reviewed inputs:

- Diagrams/rocketrental-mindmap revision 4, including **f-portals** (manager dashboard and mobile tenant portal) and **c-ux** (mobile-first tenant experience and accessibility). The diagram has no repository file references requiring additional reads.
- All five supplied examples: property returns, tenant detail, portfolio payments, portfolio returns, and lease detail. Their useful patterns are clear navy navigation, compact labels, aligned amounts and visible actions. Their excess whitespace, tall statistic cards, heavy shadows and long undifferentiated tables are not the target.
- The current app source, route entry points, forms, workspace panels, shared UI, and route boundaries. Source inspection covers states that would require changing live data to reproduce.
- The existing personal Edge session, operated with Windows MCP under the desktop lease. Read-only views observed include dashboard, Properties, Tenants, Applications, Payments, Returns, Maintenance, Documents, Integrations, the new-lease unit picker and the completed lease workspace. Also observed all four tenant routes at 390px, sign-out confirmation and the signed-out notice; the manager session was restored afterward.
- Supplemental configured Playwright checks cover responsive navigation, chart data disclosure, UI examples and automated accessibility. These are separate from the native Edge evidence.

No rents, leases, applicants, repairs, provider connections or files were created, edited or deleted during this review. Sign-in creates normal session records. Uploads, payment/refund/payout submission, screening, messages and invitations were not triggered.

## Shared visual and interaction decisions

- Preserve Inter body text and the existing Space Grotesk heading setup, navy `#1e3a8a`, white surfaces and restrained warm accent. Muted text is now `#526176` for stronger readability.
- Reuse existing tokens: `--rr-page-max:1120px`, 32px desktop/16px phone gutters, 16px gaps and card padding, 12px card radius; 26px page titles, 18px section headings, 15px compact panel headings, 24px metrics (dashboard lead amount 28px). Avoid page-size hero blocks and decorative statistic icons.
- Cards use a thin border and no drop shadow. Rows, rules and whitespace provide grouping. Reserve the drawer shadow for the modal layer.
- Keep one clear primary action, descriptive secondary destinations and visible text for status. Tabular numerals support comparisons; dollar amounts retain existing calculations.
- Desktop sidebar docks at 1024px. Below that, the 280px drawer has a scrim, close control, dialog semantics, contained keyboard focus and scroll locking. At phone widths header actions fill a second row; tablet actions stay beside the heading when they fit.
- Coarse pointers get 44px interactive controls and 16px form text. Tabs remain horizontally scrollable, not compressed or silently clipped. Global focus rings are 3px with offset; the dark sidebar uses white.
- Tables need scoped headers and a labelled scroll region when horizontal overflow is necessary. The dashboard's exact-amount disclosure provides a reusable pattern for chart alternatives.
- Shared leasing panel CSS now consumes the established surface, border, muted, spacing, heading and metric tokens. Follow-up areas should add area-local classes instead of rewriting `leasing.module.css`, workspace shell styles or global tokens concurrently.
- Foundation owns shared state shape and focus behavior; tenant/auth and feature areas own their contextual message, permission and recovery destination. This does not authorize changes to their pages from the foundation task.
